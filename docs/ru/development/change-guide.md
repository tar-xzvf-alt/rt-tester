# Руководство по изменениям

[English](../../development/change-guide.md)

Эта карта помогает найти всех потребителей существующего поля или поведения.
Она описывает сопровождение текущих интерфейсов, не проектирует новые. Начните
с [архитектуры](architecture.md) и [разработки/тестирования](development-and-testing.md).

## Матрица влияния изменений

| Изменение | Какие код и данные рассматривать вместе | Проверки и документация |
|---|---|---|
| Параметр/default receiver | `config.py`, allowlist/преобразования `config_loader.py`, границы сборщика и CLI overrides, генерируемая runner конфигурация receiver | Проверить заданные и подтверждённые значения; обновить руководство receiver, профили и оба языка |
| Параметр INI стенда | Загрузка/проверки `ConfigParser` нужного runner и генерация команд; `central_observability.py` для общих полей наблюдения | Проверки функций с mock-командами; обновить примеры режима/reference с редактируемыми адресами и путями вывода |
| Интервал, размер группы, тайм-аут, размер хвоста | Преобразование `[measurement]` runner, ограничения receiver, `START` JSON, проверки/echo прошивки и счётчики | Сравнить парные профили; проверить целостность и принятые параметры; обновить статистику/методику, не только default |
| Serial-поле или статус прошивки | `arduino-meter.ino`, `measurement.cpp`, `serial_comm.py`, dispatch/start/stop receiver, преобразование в БД, потребители метрик | Сохранить JSON-строки и семантику сессий; unit-проверки плюс отдельно отмеченная аппаратная serial-проверка |
| Stdout receiver / стартовый шлюз | Вывод готовности/прогресса receiver и matching/callback/stdin supervised runner | Запустить `test_run_stand_measurement.py`; обновить примеры вывода на обоих языках |
| Поле/схема SQLite | CREATE/ALTER и запись `database.py`, сводки обоих GPIO runner, импорт/сводка trace, запросы графиков, явные колонки/схема merger | Временные fixtures старой/новой схемы; проверить defaults, единицы, ключи, замену и потери merge; обновить SQLite-reference/статистику |
| Метрика/label Prometheus | `metrics_server.py`, помощник запросов, trace-importer, генерируемая/статическая конфигурация Prometheus, дашборды; исторические помощники — только если используются | Проверить имена выдачи/запросов и выбор платы без серверов; реальные scrape/remote-write/дашборды проверяются отдельно |
| Bundle/валидация/публикация cyclictest | `run_linux_benchmark.py`, схема/version/хеши manifest, проверки и sidecar `publish_cyclictest.py`, внешний импортёр `rt-results` | Проверить некорректные/изменённые/неполные bundle и повторную отправку; согласовать публикацию/методику с совместимостью импортёра |
| Профиль/backend/приоритеты | `configs/stands/`, backend/start/cleanup runner, внешние mappings платы и пути binary/module | Согласовать переменные парных экспериментов; обновить требования платы и метаданные; не заявлять новый аппаратный результат |
| Установленная команда/файл | Списки install/wrapper/`%check` в `.gear/rt-tester-tools.spec`, runtime paths, границы source-only | Сначала тесты исходников; сборка/проверка содержимого пакета — только после явного одобрения пользователя |

## Сохраняемая serial- и статистическая семантика

`START {JSON}\n` — команда прошивки; `started` — подтверждение принятых параметров.
Строка готовности supervised в stdout — отдельный контракт запуска на ПК.
Сохраняйте согласованность ID сессии в команде, группе, статусе, БД и trace labels;
проверяйте устаревшие статусы и индексацию групп с нуля. Интерактивные команды
receiver не совпадают полностью с набором команд прошивки.

Прошивка отправляет ровно заданное число запросов на группу, включая тайм-ауты.
Ожидающий запрос не отправляется повторно; отсутствие ответа увеличивает счётчик
тайм-аутов и не даёт отсчёта задержки. Среднее по всем ответам группы и RMS jitter
вычисляются до выбора хвоста; `avg_latency_us` и `min_latency_us` описывают
сохранённый худший хвост, а не всю совокупность. Размер хвоста сборщик получает
из 5%, прошивка ограничивает его доступными ответами. SQLite хранит хвост и jitter,
но не каждое serial-поле сводки. Не переосмысливайте исторические строки и не
заполняйте неизвестные метаданные как измеренные. Определения находятся в
[статистике измерений](../reference/measurement-statistics.md).

## Профили и совместимость данных

Для контролируемого сравнения согласуйте интервал, число/размер групп, тайм-аут
ответа, плату/backend и приоритеты, кроме намеренно изменяемой переменной.
Используйте разные выходные БД для сессий/профилей и достоверные `target-*`
метаданные; одной метки ядра недостаточно для подтверждения реально запущенного
ядра. При изменении имени платы проверьте preflight runner и mappings на плате.

Проверяйте профили разбором и генерацией команд, не полным запуском runner.
`--dry-run` не является API проверки без изменений файловой системы. Адреса,
пути и endpoints наблюдения в примерах должны редактироваться читателем.
Для сбора без оперативного наблюдения учитывайте синхронные запросы Prometheus
в текущем receiver; не описывайте его как сборщик без сетевых обращений.

При работе с БД учитывайте глобальный выбор первого пути, WAL-транзакции и
`INSERT OR REPLACE` для групп. Исторические миграции и колонки merger задаются
явным кодом, не распространяются автоматически из схемы. Merger пропускает
`trace_group_metrics` и не является резервной копией без потерь; сохраняйте
первичные артефакты. Для изменений тестируйте временные копии; immutable read-only
используйте только для статических данных с завершённым checkpoint.

## Двуязычное сопровождение и завершение

Обновляйте английский документ и русское зеркало в одном изменении: команды,
имена параметров, единицы, defaults, ограничения, пути артефактов и утверждения
о проверках должны совпадать. Переводите объяснения, не JSON-ключи, CLI-флаги,
метрики и машинные stdout-токены. При первом существенном употреблении в русском
пути объясняйте GPIO (цифровые линии общего назначения), PREEMPT_RT (механизмы
повышения вытесняемости ядра Linux) и latency (задержка измеряемого ответа либо
пробуждения). Переключатели языков должны разрешаться внутри `docs/`:
английский development → `../ru/development/<name>.md`; русский development →
`../../development/<name>.md`.

Запустите выборочные проверки изменяемой границы, затем полный unittest из
[разработки/тестирования](development-and-testing.md). Просмотрите локальные ссылки
обоих языков. В [валидации](../reference/validation.md) отметьте реально выполненное,
подменённые вызовы, происхождение исторических данных и ожидающие стендовые/
серверные проверки. Одобрение документации предшествует отложенной упаковке RPM;
согласие с планом само по себе не разрешает сборку.
