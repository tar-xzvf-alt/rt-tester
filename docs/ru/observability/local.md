# Локальные Prometheus и Grafana

[English](../../observability/local.md)

Используйте этот сценарий после успешного выполнения
[базовой пошаговой процедуры GPIO](../usage/standalone-gpio-walkthrough.md).
GPIO — ввод/вывод общего назначения. Prometheus собирает временные ряды
в реальном времени; Grafana отображает их. Ни один из них не заменяет артефакт
эксперимента SQLite. Здесь не нужны центральный сервер и перенаправление SSH
(защищённого удалённого соединения).

```text
Arduino → приёмник :9101 ─────┐
                             ├→ Prometheus на ПК :9092 → Grafana на ПК :3002 → браузер
целевой node_exporter :9100 ──┘
приёмник → основная база SQLite (независима от хранилища панели)
```

## 1. Подготовьте ПО и свой локальный профиль

Установите доступные пакеты ALT на ПК:

```bash
apt-get install prometheus grafana
command -v prometheus grafana-server
```

Сценарий запуска ожидает домашний каталог Grafana `/usr/share/grafana`.
Адаптируйте установку, если ваш пакет использует другую структуру. Порты 9101,
9092 и 3002 должны быть свободны; сейчас порт приёмника фиксирован на 9101.
Одной настройки опроса `receiver-port` недостаточно для изменения порта приёмника.

Используйте скопированный/адаптированный `visionfive2-gpio-local.conf` из
пошаговой процедуры. Сохраните настройки измерения/целевой системы базового
эксперимента. Ключевое отличие:

```ini
[observability]
remote-write-url =
prometheus-port = 9092
prometheus-url = http://127.0.0.1:9092
receiver-port = 9101
grafana-managed = true
grafana-port = 3002
grafana-url = http://127.0.0.1:3002/d/rt-standalone-gpio
```

Сохраните абсолютные пути PID (идентификаторов процессов), журналов, данных и
конфигурации полного профиля и редактируемый `node-exporter-target`. Пустой URL
remote write (удалённой записи метрик) отключает центральную передачу.
`node_exporter` должен работать на целевой системе до сбора. Сценарий запуска
создаёт конфигурацию опроса, источник данных с UID (уникальным идентификатором)
`rt-gpio-prometheus` и файловую настройку панелей из установленных ресурсов;
для нового управляемого экземпляра Grafana ручной импорт автономной панели не нужен.

## 2. Выполните короткую проверку панели

Запускайте из сохранённого каталога эксперимента:

```bash
OBS_SESSION=$(date +%s)
rt-tester-run-gpio --config ./visionfive2-gpio-local.conf \
  --session-id "$OBS_SESSION" --groups 10 \
  --db "$PWD/.rt-tester-example/local-observability.db"
```

Используйте несколько групп: при эталонных настройках группа номинально занимает
около 1.5 секунды, а метрики текущих значений Arduino опрашиваются каждые 500 мс.
Запуск одной группы может завершиться до её попадания в опрос. Скопируйте
напечатанные идентификатор сеанса и URL Grafana.

## 3. Проверьте путь данных во время запуска

Из другого терминала ПК:

```bash
curl -fsS http://127.0.0.1:9101/health
curl -fsS http://127.0.0.1:9101/metrics
curl -fsS http://127.0.0.1:9092/-/ready
curl -fsS http://127.0.0.1:3002/api/health
```

После первой завершённой группы `/metrics` приёмника должен содержать
`arduino_latency_mean`, `arduino_latency_avg` и `arduino_jitter` с `session_id`,
соответствующим запуску. До этого ответ может быть пустым. Приёмник слушает
все интерфейсы ПК; локальный опрос использует петлевой интерфейс.

На `http://127.0.0.1:9092/targets` оба задания во время сбора должны иметь
состояние UP (доступны). Используйте страницу запросов Prometheus или стабильный
HTTP API (программный интерфейс):

```bash
curl -fsSG http://127.0.0.1:9092/api/v1/query \
  --data-urlencode 'query=up{job="arduino_latency"}'
curl -fsSG http://127.0.0.1:9092/api/v1/query \
  --data-urlencode 'query=up{job="runtime_node_exporter"}'
```

Оба значения должны быть `1`, пока точки доступа работают. Запросите
`arduino_latency_avg{session_id="YOUR_SESSION_ID"}` и подтвердите свой сеанс.
После выхода приёмника его `up` становится 0, а текущие значения со временем
исчезают; выберите временной диапазон эксперимента или запросите
`max_over_time(arduino_latency_avg{session_id="YOUR_SESSION_ID"}[1h])`.
`monitor`, `collector` и `stand` — внешние метки удалённой доставки, а не метки
локально опрошенных данных, поэтому не фильтруйте локальные запросы по ним.

## 4. Проверьте Grafana и сохраните данные

Откройте напечатанный URL:

```text
http://127.0.0.1:3002/d/rt-standalone-gpio?var-session_id=YOUR_SESSION_ID
```

Выберите плату `visionfive2`, фактический сеанс и временной диапазон запуска.
Автономная панель показывает задержку хвоста, джиттер (разброс задержек) и
CPU/память целевой системы. «Average» («Среднее») означает среднее худшего хвоста
(наибольших сохранённых задержек); экспортируемое среднее всей группы — другая
метрика. См. [статистику измерений](../reference/measurement-statistics.md).

Если данные есть в Prometheus, но Grafana пуста, проверьте UID источника данных
`rt-gpio-prometheus`, URL `http://127.0.0.1:9092`, переменные/временной диапазон
панели и журналы Grafana. Если порт уже занят неуправляемой Grafana, сценарий
использует её повторно и не настраивает автоматически источник данных/панель;
настройте этот экземпляр явно или остановите перед управляемым примером.

Сохраняйте SQLite, отредактированный профиль, журналы, версии и заметки.
Дополнение CPU/памятью может быть неполным; проверьте покрытие перед сопоставлением
с задержкой. Метрики текущих значений Prometheus описывают последнюю группу,
а не архив всех групп без потерь.

## 5. Остановите управляемый мониторинг

Обработчик измерений удаляется автоматически; мониторинг остаётся доступным.
Из того же каталога эксперимента с тем же профилем:

```bash
rt-tester-run-gpio --config ./visionfive2-gpio-local.conf --stop-observability
```

Это останавливает процессы, указанные PID-файлами профиля. Данные SQLite или
TSDB (базы временных рядов) не стираются, посторонние службы дистрибутива не
останавливаются. Для удалённой доставки метрик переходите к
[центральному мониторингу](central.md).

## Обобщённый dashboard стенда с супервизором

`grafana/dashboards/rt-supervised-overview.json` (UID `rt-supervised-overview`)
показывает GPIO latency и RMS jitter на всю ширину, отдельные trace-этапы,
целостность групп и нагрузку выбираемой платы с ПЛК runtime. В нём нет фиксированных
моделей плат, адресов или сетевого интерфейса. Существующий file provider подключит
его при provisioning пакетного каталога dashboards; в неуправляемую Grafana можно
импортировать JSON и настроить скрытый Prometheus datasource. Прежние `rt-trace-stages`
и лабораторный dashboard сохранены.

Выбирайте переменные в таком порядке:

1. **PLC runtime board** — `board` из trace-серий supervisor для `runtime_wait`,
   а не из отображаемых метаданных receiver.
2. **Kernel** — сохранённые версии ядра в сессиях этой платы или `All`.
3. **Stress** — сохранённый сценарий нагрузки: обычно `off` / `on` или `All`.
4. **Session** — сессии выбранной платы, ядра и нагрузки или `All`.
5. **Stage statistic** — `min`, `avg`, `max` или `All`.

Ядро и нагрузка берутся из `arduino_session_info` receiver, связанной с сессиями
supervisor по `(stand, session_id)`. Это заданные для прохода `target-kernel`
и `target-stress`, а не независимое подтверждение `uname -r` или работы stress-процесса.
Нагрузка означает заявленный сценарий искусственной нагрузки, не порог CPU%.
Dashboard не переписывает старые данные и не определяет PREEMPT_RT по строке
версии ядра. Рядам без метаданных сессии не назначается вымышленная версия ядра
или сценарий нагрузки.

Latency, jitter, счётчики и этапы контроллера ограничены сессиями выбранного
runtime с выбранными условиями. Контроллер определяется автоматически по сессиям,
отдельного переключателя нет. CPU, память, load и сеть показывают только runtime-плату; это текущие
метрики машины, а не измерения с меткой сессии. Несколько exporter instances
с одинаковой меткой платы показаны отдельными рядами. Для старой сессии выберите
также её время. Выбор старого ядра не превращает текущие показатели машины
в исторические результаты того прохода. Сеть показывает каждый интерфейс,
кроме loopback, отдельным рядом, без переключателя интерфейса.

Технические переменные скрыты из панели фильтров. В настройках dashboard →
Variables при установке задайте `datasource`, при необходимости ограничьте
`stand`, а константу `freshness_seconds` (по умолчанию `60`) установите больше
длительности группы с запасом на scrape. `stand` по умолчанию равен `All` и допускает
отсутствие метки на локальном сборщике. На центральном сборщике ограничьте скрытый
выбор стенда, чтобы разделить машины одного типа платы. Эти параметры не меняют
настройки измерения. Варианты фильтров и принадлежность сессий определяются по
метаданным выбранного временного диапазона, даже если в его конце эти ряды уже неактивны.

Требования к scrape-меткам совпадают с конфигурацией stand runner:

| Endpoint | Требуемые метки |
| --- | --- |
| Supervisor trace | `board=<runtime-плата>`, `role="supervisor"` |
| Controller trace | `board=<плата контроллера>`, `role="controller"` |
| Runtime node_exporter | `board=<runtime-плата>`, `role="runtime"` (также допускается `supervisor`) |
| Arduino receiver | `arduino_session_info` с `session_id`, `kernel`, `stress`; job доступности `arduino_latency` |

На сборщике нескольких стендов задайте согласованную метку `stand` всем endpoints
каждого стенда. Локальный runner использует external labels только для удалённой
передачи, поэтому локально оставьте скрытый `stand` равным `All`. В старые scrape-примеры
без `board` или `role` нужно добавить эти метки. Trace exporters должны публиковать
`rt_trace_stage_latest_us`, `rt_trace_stage_latest_group_index` и
`rt_trace_stage_latest_timestamp_seconds`; панели целостности receiver требуют
новых счётчиков групп и времени получения. Отсутствие ряда не означает нулевой результат.

Trace `avg` относится к зарегистрированным измерениям этапа, не к худшему хвосту
Arduino. `runtime_wait` включает опрос/планирование ПЛК, а ожидание контроллера
перекрывает работу runtime. Скрытый `freshness_seconds` прекращает отображать сохранённые
latency/trace gauges после заданного возраста; не удаляет историю Prometheus,
не меняет deadlines измерения и не является явным признаком активности сбора.

## Лабораторный двухплатный стенд с супервизором

В соседнем checkout `beremiz-stand` есть `scripts/run_observed_session.py` для
конечного прохода Arduino с согласованными trace-метаданными контроллера и ПЛК.
Настройки этого лабораторного сценария:
`prometheus/repka5-k3-local.yml` и
`grafana/dashboards/repka5-k3.json`. Здесь используются
уже работающие Prometheus `:9090` и Grafana `:3000`, а не дополнительная пара
управляемых серверов из примера выше.

- Node exporters опрашиваются напрямую на платах `:9100`, trace exporters —
  на `:9201`; только receiver `:9101` работает на ПК. Нужны прямой и обратный
  IP-маршруты. В лаборатории две узкие Wi-Fi host routes перекрывают default
  VPN только для адресов плат. SSH-туннели и ProxyJump не требуются. Метки
  `board` и `role` разделяют платы даже при совпадении имён Linux.
- Receiver `:9101` экспортирует среднее всех ответов группы, статистику худшего
  хвоста, RMS jitter, целостность последней группы и накопительные счётчики
  запросов, ответов и timeout текущей сессии.
- Задайте `node-exporter-board` равным метке runtime-платы для дополнения SQLite
  данными CPU/памяти: старый запрос без фильтра может смешивать платы.
- `receiver.py --start --exit-on-stop --keep-metrics` закрывает Arduino после
  конечного прохода, но оставляет HTTP endpoint. Возраст результата определяется
  по `arduino_last_group_timestamp_seconds`; trace exporters публикуют аналогичную
  метрику `rt_trace_stage_latest_timestamp_seconds` для каждого этапа.
- Через 15 секунд без новой группы dashboard прекращает показывать текущие
  линии latency/этапов. История остаётся в Prometheus. Endpoint UP не означает
  генерацию импульсов, а накопительные счётчики сохраняют потери предыдущих групп.
- До прохода часы плат должны согласовываться с ПК. Сценарий отказывается
  запускать измерение при отклонении более пяти секунд. Длительности считаются
  внутри локального времени каждой платы; trace-этапы — **не CPU-время процессов**.
  Ожидания на разных платах перекрываются и не должны суммироваться.

Для измерений теперь используется только `rt-stand-observed-session`; две
прежние tunnel units отключены. Перезапуск службы контролируемо перезапускает
стек и выполняет новый конечный проход; генерация GPIO не включается автоматически
при входе в систему. Dashboard начинается с общей latency и RMS jitter на всю
ширину; далее — отдельные этапы с выбором сессии и min/avg/max. Это статистика
внутри каждой группы, не общее среднее сессии. Выберите также время эксперимента.
Исходные trace
файлы относятся к одному проходу и обнуляются при старте стека: при необходимости
сохраните их перед следующим проходом. SQLite и существующая TSDB не удаляются.
