# Методика сравнений cyclictest

[English](../../methodology/cyclictest-comparisons.md)

Сравнивайте запуски без нагрузки и под нагрузкой с одинаковыми настройками теста,
ядром, топологией CPU и политикой энергопотребления. Десятисекундные запуски
проверяют цепочку сбора; они не характеризуют задержку (latency) в наихудшем случае.

## Рекомендуемая серия

1. Выполните пробную проверку каждого адаптированного профиля.
2. Зафиксируйте частоту CPU или явно включите DVFS (динамическое изменение
   напряжения и частоты) в предмет исследования.
3. Используйте порядок ABBA: без нагрузки, с нагрузкой, с нагрузкой, без нагрузки.
4. Выполняйте запуски не менее десяти минут и повторите серию не менее трёх раз.
5. Проверьте выход за диапазон гистограммы, состояние целевой платы и очистку нагрузки.
6. Сравните среднее, p95, p99 и максимум по запускам и по CPU. Указывайте выход
   за диапазон и не восстанавливайте полное распределение по усечённой гистограмме
   без его учёта.
7. Сохраняйте каждый завершённый комплект. Не делайте вывод по одному максимуму.

## Пример управления частотой VisionFive 2

Исторический стенд использовал общую `policy0` для CPU 0–3 и доступные частоты
`375000 500000 750000 1500000` кГц. Сначала проверьте их на **своём** ядре/плате.
Замените `TARGET_HOST`; команды ниже изменяют состояние целевой платы с повышенными
правами. Запишите исходные значения в заметки эксперимента и обеспечьте
восстановление даже после неудачного запуска.

```bash
ssh root@TARGET_HOST '
P=/sys/devices/system/cpu/cpufreq/policy0
for f in scaling_driver affected_cpus scaling_available_frequencies \
    scaling_governor scaling_min_freq scaling_max_freq scaling_cur_freq; do
    printf "%s=" "$f"
    read -r value < "$P/$f"
    printf "%s\n" "$value"
done
'
```

Если поддерживается 1,5 ГГц, зафиксируйте политику этой частоты:

```bash
ssh root@TARGET_HOST '
set -eu
P=/sys/devices/system/cpu/cpufreq/policy0
printf "%s\n" performance > "$P/scaling_governor"
printf "%s\n" 1500000 > "$P/scaling_max_freq"
printf "%s\n" 1500000 > "$P/scaling_min_freq"
'
```

Проверяйте регулятор, минимальную, максимальную и текущую частоту до и после
каждого запуска. Настройки частоты не устраняют тепловое снижение частоты:
контролируйте охлаждение и фиксируйте температуру.

```bash
rt-tester-run-linux-benchmark --config ./idle.conf --duration 10m
rt-tester-run-linux-benchmark --config ./stress.conf --duration 10m
rt-tester-run-linux-benchmark --config ./stress.conf --duration 10m
rt-tester-run-linux-benchmark --config ./idle.conf --duration 10m
```

Добавляйте `--publish` только после настройки отдельного сервера результатов.
После завершения восстановите **записанные исходные** минимум/максимум/регулятор.
Исторические значения по умолчанию: минимум `375000`, максимум `1500000`,
регулятор `schedutil`; не предполагайте такие значения на другой установке.

## Интерпретация

Если после фиксации частоты результаты без нагрузки и с нагрузкой сближаются,
исходное различие зависело от DVFS. Если под нагрузкой результат остаётся лучше,
отдельно исследуйте состояния простоя CPU, devfreq DDR/межсоединений и размещение
IRQ. Если нагрузка ухудшает p95/p99 при той же частоте, конкуренция за планировщик,
кэш и память — возможные механизмы, а не автоматически доказанные причины.

Длительные запуски дают больше возможностей обнаружить редкие выбросы, поэтому
максимумы при разных длительностях напрямую несопоставимы. PREEMPT_RT —
конфигурация вытеснения Linux для работы в реальном времени — описывает поведение
ядра, а не экспериментально установленный гарантированный срок ответа.
См. [запуск тестов](../modes/linux-benchmarks.md) и
[публикацию](../usage/publish-cyclictest.md).
